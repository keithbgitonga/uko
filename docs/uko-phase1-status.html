What “reference coverage” means

It is not Uko? progress. It is the confidence that we understand a Bolt behaviour precisely enough to specify, build and test Uko? against it. 100% would mean we know the screens, API contract, states, edge cases and policy values for that area. 73.5% means the core is solid and the remaining gaps are specific and small — not open-ended discovery.

02What Bolt actually does

Six findings that matter for Uko?, in plain language. These are behaviours we observed in the pinned builds, not marketing copy.

Finding 1 · scheduling
Scheduling is a server contract, not a screen
The rider app does not decide which times are valid. It asks the backend for a pickup-time screen and ETA; the server returns valid times, prerequisites, banners and errors (“area not supported”, “distance too long”, “payment method required”). Uko? should build it this way so operations can change rules without an app release.
Finding 2 · scheduled rides
Scheduled rides are a separate product
Bolt has a dedicated scheduled-ride API family (`createScheduled`, `getScheduledRideEta`, `getScheduledRidePickupTimeScreen`, `editScheduledRide`, `cancelRide`) plus a dedicated driver “scheduled requests” surface and server-driven detail screens. It is not an on-demand ride with a future timestamp.
Finding 3 · order lifecycle
The trip is a 14-state machine
Driver states include waiting-for-confirmation, driver-creating-order, accepted, arrived, driving-with-client, waiting-on-stop, client-cancelled, driver-rejected, client-did-not-show, payment-booking-failed and finished. A separate rider-confirmation gate (WAITING → CONFIRMED / REJECTED / TIMEOUT) reduces no-shows — a good fit for scheduled rides.
Finding 4 · pricing
Three pricing modes, not one
Fixed upfront price, surge confirmation, and a bid/counter-offer marketplace: riders can update an offer (`rides/order/updateOffer`), drivers respond with counter-offers inside server-owned price bands with expiry timestamps. Uko? can ship fixed price + surge first, but the data model should reserve bids.
Finding 5 · payments & safety
Payments are a state machine; safety is a stack
Card payments use dedicated 3-D Secure challenge endpoints, Google Pay tokens and full instrument lifecycle. Safety includes SOS registration, incident reporting, masked in-app calling, and (driver side) audio recording and speech-to-text. M-Pesa must follow the same challenge/callback shape.
Finding 6 · runtime
The two apps are deliberately different
Realtime is MQTT with a polling fallback in both. But the rider app has no background location, while the driver app requires background location, screen overlay, usage access and foreground recording. Navigation is Mapbox in the driver app, Google Maps in the rider app.

Terminal exceptions: rider cancelled, driver rejected, driver did not respond, client did not show, payment booking failed. Every transition should write a durable ride event in Uko? — that is what powers support, disputes and on-time metrics.

What we did not find
  • No client-side scheduling limits — the window and lead time are server policy.
  • No hard-coded offer timeout — the server sends a timestamp.
  • No certificate pinning declared in network-security config (it may exist in code).
  • No dispatch console in the consumer apps — that is Uko?’s own product.
What it means
  • Uko? should own scheduling rules in the backend from day one.
  • Offer timeouts should be server-supplied, not app constants.
  • Don’t copy “security theatre” claims — verify code-level behaviour before promising pinning.
  • The dispatch console is a genuine differentiator we design ourselves.

04What this means for Uko?

Seven architecture decisions the evidence now supports. Together they are the “architecture delta” we will formalise in the PRD.

#DecisionWhat changes versus the original plan
1Server-driven schedulingAdd a scheduling service with a pickup-time-screen endpoint, ETA endpoint, prerequisites/banners, and an explicit error taxonomy. Rules live in the backend, per zone — not in the app.
2Separate scheduled-ride resourceScheduled rides get their own API family and data model (`Booking`), distinct from on-demand `Ride`. Editing, cancellation reasons and review screens are first-class.
3Bid-ready pricing modelShip fixed price + surge; reserve `Offer`, `Bid`, `PriceBand` entities and an `updateOffer` endpoint so price bidding can arrive in V2 without a schema rewrite.
4Payment state machineM-Pesa STK is an async challenge with callback/polling states, like 3-D Secure — not fire-and-forget. Add instrument lifecycle, a double-entry ledger and reconciliation.
5Rider-confirmation gateAdd a confirmation/pickup-code step before trip start (WAITING → CONFIRMED / REJECTED / TIMEOUT). Recommended for scheduled rides; reduces no-shows.
6MQTT + polling fallbackKeep the planned MQTT primary channel and add the polling fallback we observed. Location pings are ephemeral; ride events are durable.
7Driver-app policy decisionsBackground location, screen overlay and in-trip recording need product and Play-policy decisions early. Mirror Bolt’s split: rider foreground-only, driver background + overlay.
MVP impact
What gets added to Phase 3
Scheduling service + pickup-time screen; scheduled-ride resource; confirmation gate; M-Pesa challenge/callback state machine; bid-ready entities (no UI); polling fallback; notification taxonomy. Estimate: +1–2 weeks to the original core-MVP window.
What stays out
Deliberately deferred
Price-bidding UI and matching, in-app audio recording/STT (V1.1), calendar suggestions (V1.1), business/work profiles, cross-app white-label support, multi-country configuration.

The net effect: Uko? is not a Bolt clone and should not chase 100% parity. The evidence tells us where Bolt’s real complexity lives — scheduling, order state, payment challenges, safety — so we can match the behaviour that users expect while deliberately designing the dispatch console and local M-Pesa experience ourselves.

06Glossary and reading guide

Short definitions for the terms used in this brief and the evidence documents.

TermMeaning in this project
APKThe Android app package file. We analysed the official released packages; both are pinned by hash so the evidence cannot drift.
Pinned buildA specific app version stored with its SHA-256 hash and signing certificate, so every finding can be traced back to an exact binary.
DEXThe compiled-code format inside an APK. Class names, strings and structure can be read without running the app.
ManifestThe app’s declaration file: permissions, screens, services, deep links and integrations.
Deep linkA URL or scheme (e.g. bolt://) that opens a specific app screen. Important for notifications, marketing and cross-app flows.
MQTTA lightweight realtime messaging protocol. Both Bolt apps use it for live order and chat updates, with a polling fallback.
3-D Secure (3DS)The card-payment challenge step. Bolt has dedicated backend endpoints for it; Uko?’s M-Pesa flow should follow the same challenge/callback shape.
Price biddingA pricing mode where the rider changes an offer price and drivers counter-offer within server-defined price bands. Not in Uko?’s MVP, but the data model should allow it.
Reference coverageHow completely a Bolt behaviour is evidenced for specification purposes — not how much of Uko? is built.
Clean-roomImplementing from documented requirements without copying code, assets, strings or UI. This is the rule for all Uko? work.
